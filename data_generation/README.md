# Namma Pulse — Synthetic Data Generation Methodology

**Phase 2 — Data Provenance: SYNTHETIC**

---

## Data classification

| Class | Meaning |
|-------|---------|
| **REAL** | Verified from BMRCL official map, website, or public engineering specs |
| **SYNTHETIC** | Generated by a documented mathematical model; NOT real ridership data |
| **DERIVED** | Real computation on synthetic or real inputs (e.g., congestion = flow ÷ capacity) |
| **SIMULATED** | Output of what-if scenarios; explicitly framed as simulation |

Every file in `data/synthetic/` carries `DATA_TYPE = SYNTHETIC` in each row.

---

## Why synthetic data?

Bengaluru Metro does not publish per-station, per-time-slot ridership data in
a machine-readable format accessible for academic/portfolio use.  The project
therefore generates synthetic demand using a documented, reproducible
methodology — rather than claiming to use real data that does not exist.

**The credibility of this approach rests entirely on transparency:**
the methodology is documented here, the parameters are visible and tunable,
and the generation is reproducible from a fixed seed.

| File | Content | Rows |

## Generation pipeline (step by step)

### Step 1 — Station weight assignment

Each of the 84 graph nodes is assigned a **station type** from:
`{residential, commercial, IT, educational, transit_hub, industrial, mixed}`

These types are **hand-labeled from general knowledge of Bengaluru geography**.
They are NOT from BMRCL surveys or travel-demand studies.
The full assignment is in `src/demand/station_characteristics.py`.

Each type has four directional weights `(origin_AM, dest_AM, origin_PM, dest_PM)`
representing how active the station is as a trip origin or destination during
morning and evening periods.

**DATA CLASS: ASSUMPTION**

---

### Step 2 — Gravity model (base OD demand)

For each origin–destination pair `(O, D)`:

```
base_demand(O, D) = scale × w_O × w_D / (1 + α × d(O,D)^β)
```

Where:
- `w_O`, `w_D` = base activity weights for origin and destination station types
- `d(O, D)` = shortest-path hop count (graph edges, unweighted)
- `α = 0.3` (distance decay scale)
- `β = 1.5` (distance decay exponent)
- `scale = 18.0` (global calibration factor)

This is a standard **gravity model** — the same family of models used in
real transport planning.  Applied here with synthetic station weights.

**Calibration anchor:** The global scale factor is tuned so that total
simulated daily system ridership lands in approximately 600k–800k passengers,
consistent with the general order of magnitude reported in Bengaluru Metro
press coverage (2024–2025).  This is a rough anchor, not a precise figure.

**DATA CLASS: SYNTHETIC (documented methodology)**

---

### Step 3 — Temporal shaping

The base demand is multiplied by a **time-of-day curve** for each 15-minute slot
(96 slots per day, 00:00–23:45).

The curve is modelled as a **mixture of Gaussians**:

**Weekday:**
- Morning peak: Gaussian centred at 09:15, σ ≈ 36 min, amplitude 0.82
- Evening peak: Gaussian centred at 19:00, σ ≈ 45 min, amplitude 0.68
- Midday bump: Gaussian centred at 13:00, σ ≈ 30 min, amplitude 0.12
- Off-peak baseline: 0.18 (relative to peak = 1.0)
- Service-closed hours (before 06:00): 0.0

**Weekend:** Later, flatter single midday peak (~12:30), mild evening bump.
**Holiday:** ~47% of the weekend curve (approximately 40–50% of normal demand).
**Event day:** Weekday curve plus surge in evening slots 68–73 (17:00–18:30).

**Calibration anchors:**
- Purple and Green lines reported as overcrowded during peak hours in 2025
  (BMRCL, media coverage).  The model produces HIGH/CRITICAL congestion
  bands at peak for these lines — consistent with this qualitative fact.
- Metro operating hours approximately 06:00–22:00 (BMRCL schedule — REAL).

**DATA CLASS: SYNTHETIC (documented methodology)**

---

### Step 4 — Directional time weights

During AM peak, origin weights for **residential** stations are boosted and
destination weights for **IT/commercial** are boosted (people travel to work).
This is inverted for PM peak.

These are modelling assumptions, not measured commuter flow data.

---

### Step 5 — Stochastic noise

Per-slot demand is multiplied by a log-normal noise factor:

```
noise ~ Normal(μ=1.0, σ=0.10)
```

This adds ±10% random variation per slot, ensuring:
- The synthetic data is not perfectly deterministic (more realistic for ML training).
- The noise is seed-controlled and reproducible.

**Validation check:** If MAE on the ML model (Phase 3) is suspiciously near-zero,
the noise_std parameter should be increased — that would indicate the ML is
simply learning the deterministic demand curve.

---

### Step 6 — Event-day surge

On event days (e.g., IPL matches at Chinnaswamy Stadium), a station-specific
surge multiplier is applied to demand involving nearby stations:

| Station | Surge factor |
|---------|-------------|
| MG Road (PL18) | 1.8× |
| Cubbon Park (PL19) | 1.6× |
| Vidhana Soudha (PL20) | 1.4× |
| Trinity (PL17) | 1.3× |
| Majestic (PL22, GL17) | 1.2× |

**Note:** Chinnaswamy Stadium is near MG Road, approximately 1.5 km walking
distance.  This is general geographic knowledge — REAL.  The surge multipliers
are ASSUMPTIONS.

---

### Step 7 — Flow assignment (OD routing)

OD demand is distributed onto edges by routing each pair along its shortest path:

1. Pre-compute all-pairs shortest paths using NetworkX (unweighted hop-distance).
2. For each `(O, D, slot)` with demand > 0.5 passengers:
   - Traverse the pre-computed path.
   - Add `demand` to each edge the path crosses.

**DATA CLASS: DERIVED (real routing computation on synthetic demand)**

---

### Step 8 — Congestion calculation

```
congestion_pct(edge, slot) = flow(edge, slot) / capacity(slot) × 100
```

Capacity assumptions (**DATA CLASS: REAL for specs, DERIVED for result**):
- Train capacity: **1,000 passengers per 6-coach train**
  - Source: BMRCL Bombardier Movia fleet specifications.  **REAL.**
- Peak frequency: 1 train per 5 min → **3 trains per 15-min slot** → capacity 3,000/slot
  - Source: Approximate from BMRCL schedule.  **DOCUMENTED ASSUMPTION.**
- Off-peak frequency: 1 train per 10 min → **1.5 trains per 15-min slot** → capacity 1,500/slot
  - Source: **DOCUMENTED ASSUMPTION.**

**Congestion bands:**

| Band | Range |
|------|-------|
| LOW | 0–50% |
| MEDIUM | 50–80% |
| HIGH | 80–100% |
| CRITICAL | >100% (overflow) |

---

### Step 9 — Delay event generation

Synthetic delay events are generated using a Bernoulli process:

```
P(delay | edge, slot) = BASE_PROB × congestion_multiplier × peak_multiplier × interchange_multiplier
```

Parameters:
- `BASE_PROB = 0.02` (2% chance of a delay on any edge in any slot)
- Congestion multipliers: LOW 1×, MEDIUM 1.8×, HIGH 3×, CRITICAL 5×
- Peak-slot multiplier: 1.6×
- Interchange-edge multiplier: 2.5×
- Delay magnitude: log-normal (median ≈ 4 min, mean ≈ 5 min)
- Causes: CROWDING (50%), SIGNAL_HOLD (25%), PLATFORM_BLOCK (15%), MAINTENANCE (10%)

**DATA CLASS: SYNTHETIC**

## Reproducibility

The pipeline uses `numpy.random.default_rng(seed)` throughout.

```bash
python scripts/generate_data.py --seed 42 --days 7
```

Running with the same `--seed` value always produces identical outputs.
Different seeds produce different noise realizations.

---

## Sanity checks

The pipeline and `tests/test_demand.py` verify:

- [ ] No negative demand
- [ ] No impossible congestion percentages (≥ 0%)
- [ ] Peak demand > off-peak demand (by slot)
- [ ] Weekend total demand differs from weekday (at least 5%)
- [ ] Reproducibility: same seed → identical total demand
- [ ] Different seeds → different outputs (noise is functioning)
- [ ] All 84 station IDs appear in station_demand.csv
- [ ] All rows carry `DATA_TYPE = SYNTHETIC`
- [ ] Transit hub stations generate more demand than peripheral residential

## Potential weaknesses

| Issue | Mitigation |
|-------|-----------|
| Gravity model may produce "too clean" demand | Stochastic noise ±10% added; different seeds produce visibly different daily profiles |
| Station type labels are assumptions | Fully documented in station_characteristics.py; tunable |
| No real ridership data for cross-validation | Rough calibration against media-reported system-level ridership (~600k–800k/day) |
| Transfer time = 0 in shortest-path routing | Phase 3 will use ML-predicted travel times with configurable transfer penalties |
| OD routing uses shortest path only | Phase 4 will implement Yen's K-shortest for multi-objective routing |
